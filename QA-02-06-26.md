# Manual QA Observations - 2026-06-02

## QA-001: Add a direct NOC delete shortcut with scoped delete modes

### Status

Open triage

### Context

Deleting a team currently works through the NOC command palette, for example:

```text
p
delete team <project>
enter
```

This is safe but not simple enough for a frequent NOC operator action.

### Observation

The NOC should support a direct delete shortcut, preferably the actual `Delete`
key, while keeping the operation preview-first and confirm-gated.

### Expected Behavior

When the operator presses `Delete` on a project/team/profile row, the NOC should
open a delete mode chooser:

- `profile only`: delete the selected configured team profile.
- `all team config`: delete all configured team profile files for that project.

Both modes should show a concrete preview before execution.

### Safety Requirements

- `profile only` deletes `.amq-squad/team.json` for `default`, or
  `.amq-squad/teams/<profile>.json` for a named profile.
- `all team config` deletes all configured team profile files for the project.
- Neither mode deletes AMQ sessions, briefs, `.agent-mail`, `team-rules.md`, or
  pointer stubs.
- `all team config` should require stronger confirmation than `y`, such as
  typing the project name.
- Keep the palette path as a fallback.
- Avoid `d` or `D` as the shortcut because those already map to drain and DLQ.

### Suggested Acceptance Criteria

- Pressing `Delete` on a project/team/profile row opens a mode chooser.
- The chooser offers `profile only` and `all team config`.
- `profile only` previews the exact profile file that will be removed.
- `all team config` previews every profile file that will be removed.
- Cancelling leaves all files untouched.
- Confirming `profile only` removes only the selected profile file.
- Confirming `all team config` removes only configured profile files.
- Existing `delete team <project>` palette flow still works.

## QA-002: NOC open threads need activity sorting, clearer needs-you meaning, and an in-view legend

### Status

Open triage

### Context

In the NOC project rollup, the right-side `open threads` pane can show a long
mixed list of stale blocked, needs-you, at-risk, gated, and running context.
During manual QA, the pane included many thread rows with ages ranging from
seconds to multiple days.

### Observation

The operator could not quickly tell which open thread was newest or most
actionable.

Specific issues:

- `open threads` does not appear sorted by latest activity. Fresh rows such as
  `29s`, `45s`, and `5m` were mixed below older `1d`, `2d`, and `4d` rows.
- It is unclear why a thread older than one day still constitutes `needs-you`.
- The NOC does not provide an immediate reminder for the symbols and colors such
  as `x`, `X`, green dot, warning, gated, and degraded markers.

### Current Model Notes

Based on the current code:

- `needs-you` means an unanswered message addressed to the operator handle, or a
  declared block awaiting the human.
- `needs-you` intentionally does not age out to stale, because human action is
  still required even after a long hold.
- `APPROVE` and `GOAL-REACHED` are specific needs-you reasons.
- Glyphs are decorative; the text label is supposed to remain authoritative.

Current symbol mapping:

| Symbol | Text meaning |
| --- | --- |
| `⚠` | needs-you |
| `✕` | blocked |
| `◆` | gated |
| `◐` | at-risk or degraded |
| `●` | running |
| `○` | stopped |
| `×` | stale-blocked or old stale signal |
| `◌` | waiting |
| `⏸` | approve needed |
| `✓` | goal reached, review/close needed |
| `⏎ jump` | row can jump to a running agent pane |

### Expected Behavior

- `open threads` should sort primarily by latest activity, newest first, unless
  a deliberate attention-priority sort is visible and documented.
- If attention-priority sorting is used, the pane should expose the sort mode,
  for example `open threads: attention, newest within group`.
- A needs-you thread older than one day should explain why it still needs the
  operator, for example `needs-you: waiting for user approval since 1d`.
- The NOC should include an accessible symbol legend, likely in help or footer
  help, so the operator can quickly decode glyphs and colors.
- The legend should work in no-color and monochrome terminals.

### Suggested Acceptance Criteria

- Open-thread rows are newest-first by default, or the active sort mode is shown.
- Fresh rows are not buried below multi-day stale rows without explanation.
- Needs-you rows include the reason and age in a way that explains why the state
  has not decayed.
- Help or footer legend documents `needs-you`, `blocked`, `gated`, `at-risk`,
  `running`, `stopped`, `stale-blocked`, `waiting`, `APPROVE`, and
  `GOAL-REACHED`.
- The same legend is available with `NO_COLOR` or ASCII fallback.

## QA-003: Project-level needs-you can look false-positive when the live team is running and not waiting

### Status

Open triage

### Context

Manual QA saw the NOC row render `needs-you taboola-pm-os`, but inspecting the
active team made it look like nothing currently needed the operator. The active
team was running.

Follow-up command evidence from the installed RC:

```sh
amq2 status --project /Users/omri.a/Code/taboola-pm-os --session beta-vault-context
```

showed:

```text
cpo         live
cto         live
senior-dev  live
qa          live
```

But:

```sh
amq2 noc --root /Users/omri.a/Code --filter project:taboola-pm-os --json
```

reported project rollup counts including:

```json
"needs_you": 5
```

And:

```sh
amq2 threads --project /Users/omri.a/Code/taboola-pm-os --session beta-vault-context --limit 30
```

showed five `needs-you` rows whose latest activity was 1 to 4 days old, while
the same session was live with all four active members reachable.

### Observation

The NOC currently treats old operator-addressed threads as live `needs-you` even
when the active team is running and the operator believes there is no current
ask. This makes the project-level `needs-you` label look false-positive.

The right-side NOC digest did list reasons such as `cpo asks` and `cpo paused`,
but that did not resolve the operator question: "what do I need to do now?"

### Expected Behavior

The project row should not simply say `needs-you` unless there is a current,
actionable operator ask.

If the signal is old but intentionally retained, the UI should make that clear,
for example:

- `old needs-you`
- `needs-you history`
- `needs-you: unresolved 2d`
- `needs-you: cpo asked 2d ago, no operator reply detected`

If the active team has since moved on or the latest thread state is an ack,
closeout, or agent-to-agent update, the project rollup should demote the signal
or label it as stale/historical instead of live needs-you.

### Suggested Acceptance Criteria

- A live session with all agents reachable does not show project-level
  `needs-you` unless a current thread still requires operator action.
- Needs-you classification considers whether the latest relevant message still
  expects the operator, not only whether any old message was addressed to the
  operator.
- If old needs-you signals remain visible by design, the row clearly labels
  them as stale or unresolved history.
- The detail pane explains the exact current user-needed action, or states that
  the signal is historical.
- The project rollup distinguishes live actionable needs-you from historical
  needs-you.

## QA-004: Simplify the NOC status model for operator scanning

### Status

Open triage

### Context

Manual QA on the live NOC showed a dense headline and tree like:

```text
70 squads · 1 live · 12 needs-you · 2 at-risk(live) · 17 blocked(live) · 17 at-risk(stale) · 32 blocked(stale) · 3 gated(stale)
```

The tree mixed running agents, needs-you rows, stale blocked rows, at-risk
counts, gated counts, old thread symbols, and fresh thread symbols in one view.

### Observation

The current model exposes too many internal workflow categories at the primary
scan level. It may be technically accurate, but it is not clear enough for a NOC
operator who needs to answer one question: "what do I need to do now?"

The operator expectation is simpler:

- Green means the team is running.
- `needs-you` means Claude Code or Codex is waiting for the operator to approve
  something, pick an interactive menu option, answer a question, release scope,
  or take another explicit action.
- `blocked` means the team is not working or something is off.
- Grey means stale, stopped, historical, or otherwise not live attention.

### Expected Behavior

The NOC should make the primary row state simple and action-oriented:

| Primary state | Operator meaning |
| --- | --- |
| `running` | Team is alive and working. |
| `needs-you` | An agent is explicitly waiting for the operator now. |
| `blocked` | The team is not making progress or has a hard problem. |
| `stale` | The signal is old, stopped, historical, or lower priority. |

Secondary details such as `at-risk`, `gated`, `blocked stale`, and
`at-risk stale` can remain available in the detail pane, help view, JSON, or an
advanced mode, but they should not dominate the first scan.

### Suggested Acceptance Criteria

- The headline uses a simpler primary summary, for example running,
  needs-you, blocked, and stale counts.
- A live running team does not look worse than it is because of old historical
  thread state.
- `needs-you` appears only when the operator has a concrete current action.
- `blocked` represents an actual non-working or hard-blocked team state, not
  old coordination history.
- Stale and historical signals are visually grey and clearly lower priority.
- Advanced state counts remain accessible but are not required to understand
  the first screen.
- The help view documents the simplified state model in operator language.

## QA-005: Recheck amq-squad leverage against the current AMQ README

### Status

Open triage

### Context

The upstream AMQ README now presents AMQ as the local interoperability bus for
agent sessions, with emphasis on cross-session and cross-project routing,
handoff state, delivery receipts, waitable handoffs, operational diagnostics,
extension metadata, and integration labels.

Reviewed source:

```text
https://github.com/avivsinai/agent-message-queue/blob/main/README.md
```

### Current Coverage

The current 2.x RC appears to cover the main operational AMQ surfaces:

- `amq_env` exposes AMQ root, project, and peer routing JSON.
- `amq_who` lists AMQ sessions and agents.
- `amq_ops` runs AMQ operational diagnostics.
- `presence` runs AMQ presence listing.
- DLQ list, read, retry, retry-all, and purge are available in the NOC.
- Receipts list and wait are available in the NOC.
- Direct operator messages can use wait-for-drained behavior.
- amq-squad launch records use the AMQ extension metadata namespace instead of
  writing into AMQ-owned mailbox directories.
- AMQ cleanup is exposed as a confirm-gated action.

### Potential Gaps

1. Route diagnostics are not first-class in the NOC.

   AMQ highlights `route explain` and cross-project federation. amq-squad uses
   route explanation internally during bootstrap, but the NOC does not appear to
   expose an operator-facing route diagnostic action for a selected project,
   session, agent, or prospective cross-project recipient.

2. Integration labels are not surfaced in thread rollups.

   AMQ integration messages can carry labels such as `orchestrator`,
   `orchestrator:symphony`, `orchestrator:kanban`, `handoff`, and `blocking`.
   The current NOC thread model does not appear to show these labels, filter by
   them, or use them as reason codes. This may be one cause of generic
   `blocked` and `needs-you` states.

3. Cross-project sender metadata is not visible enough.

   AMQ uses project metadata such as `from_project` and `reply_project` for
   federated routing. NOC thread rows and JSON should expose this context when
   present so a same-handle message from another project is not mistaken for a
   local echo or folded into the wrong squad.

4. AMQ cleanup safety should be explicitly tested against extensions.

   The README says extension directories are layer-owned and cleanup should
   leave them alone. amq-squad depends on that contract for launch records, so
   the RC should have a focused regression test or manual QA note proving AMQ
   cleanup does not remove amq-squad launch or role metadata.

### Expected Behavior

- The NOC should provide a read-only route diagnostic action, likely named
  `amq_route` or `route_explain`, for selected projects, sessions, and agents.
- Route diagnostics should show the resolved command or routing error before an
  operator sends or broadcasts a message.
- Thread rows and detail panes should surface AMQ labels and orchestrator
  context when present.
- NOC filters should support label-oriented filtering for AMQ integration
  traffic, such as `label:handoff`, `label:blocking`, or
  `orchestrator:kanban`.
- `noc --json` should expose labels, integration metadata, and project routing
  metadata when AMQ messages provide them.
- `amq_cleanup` should remain confirm-gated and should have coverage proving it
  does not remove amq-squad extension metadata.

### Suggested Acceptance Criteria

- A selected agent or session exposes a read-only `route_explain` style action.
- The action handles local, cross-session, and cross-project routes.
- Route failures are shown as diagnostics, not as silent missing commands.
- Thread JSON includes labels and project routing metadata when present.
- The NOC can filter or highlight AMQ integration traffic by label.
- Handoff and blocking labels improve state classification instead of being
  flattened into generic `blocked` or stale `needs-you`.
- AMQ cleanup tests or manual QA prove that extension metadata survives cleanup.

## QA-006: Stopped agents and stopped teams must not produce live needs-you

### Status

Open triage

### Observation

The NOC can show a stopped agent or stopped session under live `needs-you`.
That reads incorrectly: if the agent is stopped, it cannot currently be waiting
for the operator.

### Expected Behavior

- A needs-you thread from a stopped, dead, missing, or stale-only agent should
  remain visible as history, not live operator work.
- Project and session rollups should not use live `needs-you` when no active
  non-operator agent exists behind the ask.
- The detail pane should label the retained signal as `needs-you history`.

### Suggested Acceptance Criteria

- A stopped session with an old or fresh user-addressed ask renders `0
  needs-you` in the primary headline.
- The same ask can still appear in details as `needs-you history`.
- The top `NEEDS YOU` block does not include stopped-agent asks.

## QA-007: Delete-team UX should not require understanding the command palette

### Status

Open triage

### Observation

The palette path is too indirect for the common operator intent: delete a team.
Even after adding a delete shortcut, the typed choices `profile-only` and
`all-team-config` expose implementation language rather than operator language.

### Expected Behavior

- Pressing `Delete` on a configured team should be the primary path.
- If there is only one configured profile, `Delete` should open the concrete
  preview directly.
- If there are multiple profiles, the prompt should use plain choices such as
  `1 one profile` and `2 all team config`.
- The command palette can remain as a fallback, but should use the same simpler
  flow.

### Suggested Acceptance Criteria

- Single-profile delete does not ask for a mode before preview.
- Multi-profile delete accepts `1` for one profile and `2` for all team config.
- All-team-config still requires typing the project name before preview.
- All mutating delete actions remain preview-first and confirm-gated.

## QA-008: Running teams should only show needs-you for current actionable asks

### Status

Open triage

### Observation

A running team can show `needs-you` even when the visible recent thread subjects
look like acknowledgements, corrections, FYI/status notes, or closeout history.
That leaves the operator asking: "why does a running team need me?"

### Expected Behavior

- Running teams can show live `needs-you` when an agent is actually waiting for
  approval, a decision, a menu choice, scope release, or a direct answer.
- Operator-addressed ack, FYI, status, correction, or closeout messages should
  not produce live `needs-you` unless they also contain an explicit operator
  action signal.
- Details should keep explaining the reason and age when a needs-you is live.

### Suggested Acceptance Criteria

- A running session with an unread operator-addressed ack/status message does
  not render live `needs-you`.
- A running session with an approval, direct question, or explicit waiting-for
  operator signal still renders live `needs-you`.
- The top `NEEDS YOU` block only lists current actionable asks.

## QA-009: Running-agent details should provide a live-feeling latest signal

### Status

Open triage

### Observation

When selecting a running agent, the NOC should provide some sense that the agent
is alive and producing work. The idea is to show the last output or latest
signal from the agent.

- The first implementation should use existing AMQ thread/message metadata, not

## QA-010: Current live work should dominate the primary NOC state

### Status

Open triage

### Observation

A visibly running team can still render as primary `blocked` when older
coordination threads carry unresolved blocked, gated, at-risk, or historical
needs-you labels. This makes the NOC contradict what the operator can see in
the live agents: the team is working now.

### Expected Behavior

- A session or project with running agents should render as `running` unless
  there is a current actionable `needs-you`.
- Blocked, gated, at-risk, and historical needs-you counts should remain visible
  as detail/history, but should not override the primary live state.
- Session detail should lead with newest thread activity so current work appears
  before 2-3 day old unresolved history.

### Suggested Acceptance Criteria

- A running session with blocked/gated/at-risk thread history renders primary
  `running`, not `blocked`.
- JSON state/reason uses `running` for live sessions with non-needs-you history.
- The session detail open-thread list is newest-first with attention labels.
- Duplicate row detail such as `blocked blocked` is collapsed to one label.

## QA-011: NOC needs to separate current control from tactical AMQ history

### Status

Open triage

### Context

Manual QA on `taboola-pm-os / beta-vault-context` showed a live session with a
single current `needs-you` ask and many tactical AMQ threads in the right pane.
The team had finished its work roughly three hours earlier and was now waiting
on an operator release decision.

### Observation

The NOC correctly surfaced an operator ask, but the screen still felt noisy:

- The overall project/session showed `needs-you`, while every agent row stayed
  green `running`.
- The session detail listed too many threads at once.
- Long labels/integration metadata caused right-pane text to truncate badly.
- Every old thread carried explicit status text, making tactical history compete
  with the current control question.

### Expected Behavior

The NOC should balance:

- `control`: what needs the operator now.
- `visibility`: enough thread history to debug, without making history the main
  control surface.

For a session waiting on the operator, the detail pane should lead with the
current ask. Thread history should be capped, newest-first, and compact. Agent
rows should not all look calmly green when their current work context is blocked
or waiting on the operator, even if their tmux/process control is still
available.

### Suggested Acceptance Criteria

- Session detail starts with a compact `now` section.
- Session detail shows only a bounded newest-thread preview by default.
- Hidden older thread count is explicit.
- Compact thread rows do not dump long AMQ label metadata.
- Agent tree/detail state reflects current non-historical work attention before
  falling back to process liveness.
- Running agents still retain the jump affordance when their process/control
  target is available.
