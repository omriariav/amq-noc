# amq-noc 0.10 Operator Client Audit

Date: 2026-06-22

Milestone: <https://github.com/omriariav/amq-noc/milestone/2>

Workstream: `v0-10-0`

## Context

`amq-noc` 0.10.0 is the AMQ/amq-squad alignment release. The target shape is an
optional user-facing NOC client over durable AMQ and amq-squad state. AMQ and
amq-squad remain the protocol source of truth.

Current upstream floor checked during this workstream:

- AMQ: `0.38.0`
- amq-squad: `2.5.0`

Baseline verification:

- `amq-squad doctor --json`: AMQ `0.38.0` and amq-squad `2.5.0` OK; old
  `amq-noc-0-1-0` workers are stale.
- `go test ./...`: pass.
- `go run ./cmd/amq-noc --json --root /Users/omri.a/Code --filter project:amq-noc`
  emits a `noc_snapshot` with project/session/agent actions.
- `go run ./cmd/amq-noc --actions --json --root /Users/omri.a/Code --filter project:amq-noc`
  emits 57 actions, 28 mutating and confirm-required where applicable.

## Existing Coverage

### Operator Gates

Existing files:

- `internal/state/coordination.go`
- `internal/state/collapse.go`
- `internal/state/attention.go`
- `internal/state/operator_gate_test.go`
- `internal/console/noc_attn_test.go`
- `docs/operator-gate.md`

Coverage:

- `user` is the default operator handle.
- Project team metadata can override the operator handle.
- Operator-addressed questions/review/decision asks become `needs-you`.
- Stable gate threads such as `gate/<topic>` are supported by convention.
- Needs-you ownership records the asker in `NeedsYouOwner`.
- A gate clears when the latest thread message is no longer addressed to the
  operator.
- Needs-you reasons include approval, goal reached, and generic asks.

Gaps:

- The main queue still exposes attention through project/session/agent rows and
  detail panes. It does not yet have a first-class, grouped operator attention
  queue object with "who acts, thread, since when, why, next safe command" as a
  single API surface.
- Gate answered/unanswered status is inferred through latest message state, not
  emitted as a dedicated field.

Owner task: `t3`

### Operator Directives

Existing files:

- `internal/console/noc_directive_test.go`
- `internal/console/noc_conversation.go`
- `README.md`

Coverage:

- `L direct-lead` supports operator-to-lead directives.
- Live leads receive a busy-guarded pane send.
- Down leads receive a durable AMQ fallback message.
- Directive AMQ fallback uses `kind=todo`, `DIRECTIVE:` subject, and sorted
  operator/lead p2p thread.
- Tests lock that directives do not clear gates.
- Conversation mode includes operator-lead dialogue and lead-raised gates.

Gaps:

- Stale unacknowledged directives are not promoted as a distinct queue class.
- Directive acknowledgement detection exists as conversation content, but there
  is no dedicated derived field for "acknowledged on same thread by status or
  answer".
- Conflicts between an open gate and a newer directive are not yet surfaced as a
  named condition.

Owner task: `t3`

### Worker Reports To Lead

Existing files:

- `internal/state/coordination.go`
- `internal/noc/orchestration_enrich_test.go`
- `internal/cli/noc_orchestration_json_test.go`
- `README.md`

Coverage:

- Threads collapse by canonical AMQ thread.
- Message kinds are normalized into status, question, review request, review
  response, decision, answer, and todo.
- Orchestrated sessions carry lead metadata.
- Lead-down is detected when an orchestrated lead is not operational while a
  child is operational.
- CLI JSON carries orchestrated, lead, lead handle, lead down, and is lead
  fields.

Gaps:

- Worker report types are not exposed as a dedicated "worker reports to lead"
  attention section.
- Decision threads under `decision/<topic>` are visible as threads, but not
  separately grouped as decision evidence.
- `DONE:` status subjects are classified for goal-reached needs-you when
  addressed to the operator, but plain worker-to-lead DONE evidence is not yet
  first-class in the operator queue.

Owner tasks: `t3`, `t4`

### Task Store

Existing files:

- None in `amq-noc` for direct amq-squad task-store consumption.
- The workstream uses amq-squad tasks under `.amq-squad/tasks/v0-10-0`.

Coverage:

- No current NOC API reads amq-squad task state as a source.

Gaps:

- Need read-only task-store ingestion or a stable amq-squad JSON command.
- Need dependency-gated task display.
- Need mismatch detection between task state and AMQ reports.
- Need clear boundary: NOC should not mutate task state unless amq-squad exposes
  an explicit safe command for the transition.

Owner task: `t4`

### Runtime And Liveness

Existing files:

- `internal/noc/runtime.go`
- `internal/cli/noc_runtime_actions.go`
- `internal/console/noc_command_picker.go`
- `docs/runtime-actions.md`
- `internal/state/attention.go`

Coverage:

- NOC consumes `amq-squad status --json`.
- Published runtime actions are copied verbatim into CLI/TUI action surfaces.
- Session actions include status, resume preview, resume current window, resume
  new session, and stop when published by amq-squad.
- Agent actions include focus and send only when the runtime contract says they
  are available.
- The code uses the published pane id from amq-squad for focus targets.
- Stale/dead liveness is separate from attention.

Gaps:

- External lead registration details from amq-squad 2.5.0 are not explicitly
  represented beyond current lead/orchestrated fields.
- Worker liveness has row state and actions, but not a dedicated liveness board
  section grouped below operator attention.
- Missing/stale/dead workers need richer next-action text in the queue model.

Owner task: `t4`

### Delivery, Receipts, DLQ, Presence, Wake Health

Existing files:

- `internal/cli/noc.go`
- `internal/console/noc_model.go`
- `internal/console/noc_*dlq*`
- `internal/console/noc_*receipts*`
- `internal/console/noc_*presence*`
- `internal/state/files.go`

Coverage:

- CLI/TUI action queue exposes `amq_env`, `amq_who`, `presence`, `amq_ops`,
  `receipts`, `receipts_wait`, `dlq`, `dlq_read`, `dlq_retry`,
  `dlq_retry_all`, and `dlq_purge`.
- Mutating DLQ actions are confirm-required.
- Receipt wait constrains the stage to `drained` or `dlq`.
- AMQ 0.38.0 currently reports `user` as `human` in `amq who` and
  `amq presence list`.
- `amq_ops` is correctly emitted as `env AM_ROOT=<session-root> amq doctor --ops`
  because `amq doctor` does not accept `--root`.

Gaps:

- Wake/receipt health is action-oriented, not summarized into derived health
  signals.
- There is no current detection for "queued but not drained" or "drained but no
  ACK/progress after threshold".
- Need to ensure `user` human rows are never interpreted as stale agents in
  state-level scans, not only in external AMQ CLI output.

Owner task: `t2`

### Merge, Review, Release Evidence

Existing files:

- No dedicated NOC evidence model found.
- Existing action/coordination surfaces can display threads and brief context.

Coverage:

- Thread transcripts, brief display, and GitHub issue links in briefs can carry
  release context indirectly.
- Mutating merge/release actions are not present, which is correct.

Gaps:

- Need a read-only evidence model for PR URL, issue links, head SHA, CI/local
  tests, review evidence, and merge-verification verdicts.
- Need SHA-match/missing-evidence blockers.
- Need a final human-owned merge/release gate representation.

Owner task: `t4`

### Safe Operator Actions

Existing files:

- `internal/act/act.go`
- `internal/cli/noc.go`
- `internal/cli/noc_runtime_actions.go`
- `internal/console/noc_control.go`
- `internal/console/noc_command_picker.go`

Coverage:

- Operator AMQ writes are preview-first.
- Mutating actions are confirm-gated.
- AMQ identity is stripped from child process environments before sends.
- Runtime commands come from amq-squad where available.
- Action JSON distinguishes mutating, confirmation-required, template vars, and
  choices.
- Published `send` actions that need stdin body are copy/display only for CLI
  `--run-action`.

Gaps:

- Action queue is broad. The operator attention queue should select a safe next
  action per item.
- Direct operator-to-worker message actions exist, but need stronger visibility
  or labeling that these are exceptional and lead-auditable.
- Shell quoting coverage should be extended for new task/evidence/action fields.

Owner task: `t3`

## Recommended 0.10 Execution Order

1. Finish a first-class attention queue data model that reuses existing
   coordination and action data.
2. Add capability/version and AMQ health snapshots, including AMQ 0.38 `user`
   human handling.
3. Add directive acknowledgement/staleness/conflict derivation.
4. Add amq-squad task-store ingestion and AMQ report mismatch detection.
5. Add read-only release evidence ingestion.
6. Wire TUI/CLI JSON/actions around the new queue sections.
7. Extend tests from state to CLI JSON to TUI rendering.

## Upstream Boundaries

Belongs in AMQ:

- Receipt semantics and receipt stage vocabulary.
- `amq doctor --ops` JSON fields for queue, DLQ, presence, and wake locks.
- Human operator presence semantics for reserved `user`.

Belongs in amq-squad:

- Runtime action contract and external lead fields.
- Task-store JSON/API contract.
- Merge verification evidence schema and `verify merge` behavior.
- Any mutation of task state or runtime state.

Belongs in amq-noc:

- Read-only collection and correlation.
- Operator attention ordering.
- Safe copyable commands and confirm-gated UI actions.
- Human-readable grouping, previews, and evidence links.
